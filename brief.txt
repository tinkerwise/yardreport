**Maintainer Brief**

Yard Report started as a single homepage and has grown into a small multi-page Astro site — the homepage feed/scores dashboard plus dedicated pages for Schedule, Depth Chart, Around the Horn, All-Star Game, MLB Draft, and Trade Deadline (including a per-player trade-rumor recap page). Each page is a thin Astro shell with its own client-side script; there is no shared framework state across pages, only shared modules under `src/scripts/`.

The homepage's client is split into domain modules: [app.js](src/scripts/app.js) is the orchestrator (event wiring, settings, refresh, init) that imports from [feeds.js](src/scripts/feeds.js), [scores.js](src/scripts/scores.js), [sidebars.js](src/scripts/sidebars.js), [walkup-songs.js](src/scripts/walkup-songs.js), [state.js](src/scripts/state.js), [theme.js](src/scripts/theme.js), [utils.js](src/scripts/utils.js), [weather.js](src/scripts/weather.js), and [easter-eggs.js](src/scripts/easter-eggs.js). The secondary pages ([all-star.js](src/scripts/all-star.js), [draft.js](src/scripts/draft.js), [trade-deadline.js](src/scripts/trade-deadline.js), [trade-player.js](src/scripts/trade-player.js), [depth-chart.js](src/scripts/depth-chart.js), [schedule.js](src/scripts/schedule.js)) are each self-contained but lean heavily on the shared helpers in `utils.js` (player-name linking, news-card rendering, team logos, og-image resolution). [style.css](public/style.css) carries nearly all layout and component styling for every page. `updates.txt` is effectively the product backlog and prompt contract. [README.md](README.md) is intentionally public-facing and brief; this file is the home for maintainer detail.

**Player-name linking (standing rule)**

Any player name rendered anywhere on the site must be a link — active roster, minor leaguers, very recent draftees, and retired players alike. The pattern lives in [utils.js](src/scripts/utils.js): `fetchPlayerIdMap()`/`lookupPlayerId()` for fast bulk lookups against the active MLB roster, `searchPlayerId()` as a per-name fallback (covers MiLB/retired/pre-debut players via `/people/search`), `playerNameOrLookup()` to paint a link immediately when the id is known or a lookup-pending span otherwise, and `resolveNameLookups()` to patch those spans in once the async search resolves. New widgets that render a player name should use this pattern rather than plain text or a one-off link.

**What’s Fragile**

The client is now split into domain modules, so changes to one area are less likely to cascade. That said, several sensitive areas remain:
- `renderArticles()` and `renderCard()` in [feeds.js](src/scripts/feeds.js) drive most feed UX; changes here can break reader opening, read/unread state, bundles, or swipe behavior.
- `getFilteredArticles()` in [feeds.js](src/scripts/feeds.js) is the source of truth for what appears; filter bugs ripple everywhere.
- `setupEvents()` in [app.js](src/scripts/app.js) is the central event wiring point; new controls should be added carefully to avoid duplicated listeners or state drift.
- `loadScores()` in [scores.js](src/scripts/scores.js) is both a rendering surface and an interaction surface; it owns score-chip triggers, popover timing, click-to-open behavior, and async boxscore refreshes.
- Walk-up songs are shared by [scores.js](src/scripts/scores.js) and [sidebars.js](src/scripts/sidebars.js) through [walkup-songs.js](src/scripts/walkup-songs.js); keep the fallback map usable and preserve the non-blocking roster render.
- `loadOnDeck()` in [sidebars.js](src/scripts/sidebars.js) is easy to break with small date/weather changes because it mixes schedule selection, forecast logic, and widget rendering in one place.
- Score/on-deck/transactions/leaders/video/podcast all depend on third-party APIs or feeds with no formal abstraction layer, so breakage from upstream response changes is a real risk.
- There is both a dev-time JS proxy in [astro.config.mjs](astro.config.mjs) and a production PHP proxy in [rss-proxy.php](public/rss-proxy.php); feed issues may differ between local and deployed environments, especially now that the proxy also supports trusted raw HTML/text passthrough for widget enrichment and audio-enclosure extraction for the podcast widget.
- [draft.js](src/scripts/draft.js) fetches the live MLB Stats API draft endpoint (`/draft/{season}`) for the real pick order and results, falling back to the curated data in [public/draft-picks.json](public/draft-picks.json) if that fetch fails — the two shapes need to stay compatible.
- [trade-deadline.js](src/scripts/trade-deadline.js)'s mention-scanning (`findMentionedPlayers`, "On the Block", Organization Watch) is text-matching only — it flags who's being *named* in trade-rumor coverage, not who's actually being shopped. Keep the UI copy honest about that distinction if this logic changes.
- The trade-rumor recap pages ([trade-player.js](src/scripts/trade-player.js)) depend on `rumorRecaps` entries in [public/trade-deadline.json](public/trade-deadline.json), which are generated offline by [scripts/generate-trade-summaries.mjs](scripts/generate-trade-summaries.mjs) — see "AI Recap Generation" below. Nothing at runtime calls an AI API; if that ever changes, an API key must never be shipped client-side.

- event wiring / settings / refresh / init (homepage): [app.js](src/scripts/app.js)
- visual/responsive change: [style.css](public/style.css)

For safety, I’d usually preserve:
- existing filters, reader behavior, and localStorage prefs
- mobile-first constraints and content density rules
- Orioles-first prioritization in scores, schedule, and sidebar widgets
- the lightweight sidebar pattern: a single compact podcast card above the video stack, rather than a dense multi-episode media rail
- the current feed-toolbar pattern: category pills right-justified against the "Around the Horn" heading row (cloned into place, original hidden — see `relocateCategoryPills()` in feeds.js), with every other feed control (sort, date range, show read, sources) consolidated into the single header settings gear rather than a second toolbar control cluster
- the current score-chip pattern: chips act as popover triggers first, with external MLB preview/results links living inside the popover
- the current category-pill pattern: Orioles, MLB, and MiLB use logo-backed pills rather than emoji labels
- the current walk-up song pattern: known songs open in the overlay, unknown Orioles players get a Spotify search icon, and roster render should not wait on live song fetches
- the player-name linking rule described above — no unlinked player names, anywhere

**Best Next Refactors**

The domain module split is done. If we want the repo even easier to maintain, the remaining high-value cleanup would be:
- centralize MLB Stats API wrappers and response shaping (currently scattered across scores.js, sidebars.js, and the secondary-page scripts)
- extend `npm run smoke` to cover the secondary pages (Schedule, Depth Chart, All-Star, Draft, Trade Deadline), not just the homepage
- extract `state.js` mutations behind setter functions to make state changes traceable

**Stack**

- Astro 6
- Static deployment
- Modular client-side rendering and state under [src/scripts/](src/scripts)
- PHP RSS proxy for production feed fetching in [rss-proxy.php](public/rss-proxy.php)
- MLB Stats API and Open-Meteo as primary runtime data services
- Official Orioles walk-up music page plus Spotify embeds/search for player music context
- One offline, opt-in build step ([scripts/generate-trade-summaries.mjs](scripts/generate-trade-summaries.mjs)) calls the Gemini API to write trade-rumor recap summaries into static JSON — nothing at runtime or in the client bundle talks to an AI API

**AI Recap Generation**

`npm run generate:trade-summaries` scans the RSS sources for Orioles trade-rumor coverage, groups it by mentioned Orioles player, and asks Gemini for a short neutral recap of each — written into `rumorRecaps` in [public/trade-deadline.json](public/trade-deadline.json). This is a manual, offline step (not part of `npm run build` or the deploy workflow), so recaps only update when someone runs it.

- Requires `GEMINI_API_KEY` in the environment (optionally `GEMINI_MODEL` to override the default). Put both in a local `.env` file — already covered by `.gitignore` — and never commit it or paste the key anywhere that gets logged.
- Run it via: `export $(cat .env | xargs) && npm run generate:trade-summaries`
- The recap page ([trade-player.js](src/scripts/trade-player.js)) only ever reads the static JSON output; it has no knowledge of the API key or the generation process.

**Deployment**

- Official release path: push to `main`, which triggers [.github/workflows/deploy.yml](.github/workflows/deploy.yml)
- The GitHub Actions workflow runs `npm run smoke`, builds the site, and deploys `dist/` to `./public_html/yardreport/` over FTP
- The same workflow file also runs two scheduled daily health jobs:
  - smoke test + live homepage check
  - production RSS proxy/feed check
- cPanel Git Version Control is a legacy/manual fallback path, not the normal release workflow
- [.cpanel.yml](.cpanel.yml) remains in the repo only for that fallback scenario. The deploy path in it is a placeholder (`REPLACE_WITH_CPANEL_USERNAME`) — the real cPanel username was previously committed in plain text here, which is unnecessary exposure (it narrows a brute-force/credential-stuffing attempt against the hosting account down to just guessing a password). If the fallback is ever actually needed, edit the real value directly on the server side rather than committing it back.

**Cron Guidance**

Cron jobs should stay minimal because most site data is fetched client-side at runtime. The useful recurring checks are operational sanity checks, not scheduled content refreshes.

Recommended recurring tasks:
- Run `npm run smoke` after deploys and optionally once daily in CI for early warning on build/output regressions
- Run a lightweight live homepage health check daily to confirm the deployed site still returns `200`
- Run a lightweight production proxy/feed sanity check daily if RSS proxy stability becomes a concern

Not worth scheduling as cron:
- plain `npm run build` without smoke/deploy follow-through
- score refreshes, standings refreshes, video refreshes, podcast refreshes, or other freshness jobs, because those surfaces are already fetched client-side

Preferred cadence:
- per deploy: `npm run smoke`
- daily: smoke test + homepage health check
- daily: RSS proxy/feed sanity check

**Workflow Notes**

`updates.txt` is the main running spec for feature work. New ideas, shipped features, and implementation prompts should stay aligned with that file.

The main implementation surface is the `src/scripts/` module set, with `app.js` as the event/init orchestrator. When making updates, preserve readability, avoid content overload, and be careful with shared render/state logic.

The built-in smoke test is `npm run smoke`. It runs a production build and then checks that the generated homepage still includes the core UI surfaces: scores, feed, On Deck, podcast, video, standings, leaders, reader overlay, settings overlay, plus key built assets. It does not currently check the secondary pages (Schedule, Depth Chart, All-Star, Draft, Trade Deadline) — a gap worth closing if those pages start seeing more churn.

Branch usage for this repo should stay simple:
- treat `main` as the deployable branch
- use a feature/fix/docs branch for larger, riskier, or unrelated work
- keep one branch per topic
- merge back into `main` only when the change is ready, since pushes to `main` trigger deployment
- for tiny safe edits, working directly on `main` is fine

To preview a branch without merging to `main`, check out that branch and run `npm run dev` for a local preview or `npm run build && npm run preview` for a production-like local preview. Stop the dev server before switching branches, then restart it on the branch you want to inspect.

**Prompting Guidance**

The prompts that will work best with this repo are specific and scoped, like:
- “Add X to the feed toolbar without changing current mobile behavior”
- “Update the video widget playlists or rotation logic without changing theater-mode behavior”
- “Adjust the podcast card placement or feed source without turning it into a heavy media experience”
- “Refine the On Deck card to show Y and keep the current visual style”
- “Update the walk-up song fallback map without blocking roster render”
- “Implement the next unchecked item from `updates.txt`”
- “Refactor just the leaders widget into a separate module without changing output”
- “Add a new section to the Draft/ASG/Trade Deadline page using the existing page's data-file + script pattern”

The prompts most likely to cause churn are broad redesigns or “clean this all up” requests, because the codebase is functional but tightly intertwined.
